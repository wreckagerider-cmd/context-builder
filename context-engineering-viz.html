Context Engineering Fundamentals

Context is the complete state available to a model at inference time. Engineering context means curating the smallest high-signal token set that maximises desired outcomes.

Principles

Four Core Principles

Apply these every time you assemble context for an agent.

1
Informativity over exhaustiveness — Include only what matters for the current decision. Design systems that retrieve additional information on demand.
2
Position-aware placement — Critical constraints belong at the beginning and end of context where recall accuracy runs 85-95%.
3
Progressive disclosure — Load skill names and summaries at startup; load full content only when a skill activates for a specific task.
4
Iterative curation — Context engineering is not a one-time exercise but an ongoing discipline applied every time content is passed to the model.
Pattern

Progressive Disclosure in Practice

Three levels of lazy loading that keep your context lean.

🎯Level 1 — Skill Selection

Load only skill names and descriptions at startup. Activate full skill content on demand when the task explicitly matches trigger conditions.

startup: [skill.name, skill.desc]
on_match: load(skill.full_content)

📄Level 2 — Document Loading

Load summaries first; fetch full detail sections only when the task requires them. Avoid loading all documentation at session start.

docs/api_summary.md ← always
docs/api/endpoints.md ← on demand

🔧Level 3 — Tool Results

Keep recent tool results in full; compress or evict older results. Tool outputs can reach 83.9% of total tokens in agent trajectories.

last 3 results: full
older results: [ref_id + summary]
Watch Out

Common Gotchas

⚠️
Nominal window ≠ effective capacity. A model advertising 200K tokens begins degrading around 120-140K. Budget for 60-70% of the nominal window.
⚠️
Tool schemas inflate 2-3× after JSON serialisation. Ten tools with moderate schemas can consume 5,000-8,000 tokens before a single message is sent.
⚠️
Message history balloons silently in agentic loops. After 20-30 iterations, history can consume 70-80% of the window. Set a hard token ceiling and trigger compaction proactively.
⚠️
Critical instructions in the middle get lost. The U-shaped attention curve means the middle receives 10-40% less recall accuracy. Anchor safety constraints at the top or bottom.

🎭Observation Masking Rules

Apply selectively based on recency and ongoing relevance — not uniformly.

🚫
Never mask: Current task observations, most recent turn, active reasoning chains, error outputs during debugging.
⏱️
Mask after 3+ turns: Verbose outputs whose key points are already extracted. Replace with [Obs:{id} elided. Key: {summary}]
✅
Mask immediately: Duplicate/repeated outputs, boilerplate headers and footers, outputs already summarised earlier.

Section 3

Multi-Agent Architecture

Distribute work across multiple model instances, each with its own context window. Sub-agents exist primarily to isolate context — not to anthropomorphize role division.

Supervisor Pattern Swarm / P2P Hierarchical Context Isolation Consensus
Economics

Token Cost Reality

Budget for substantially higher token costs before committing to multi-agent architectures.

Single agent chat 1× baseline
Single agent with tools ~4× baseline
Multi-agent system ~15× baseline

⚡ 80% of performance variance is explained by token usage alone (BrowseComp evaluation). Model quality improvements frequently outperform raw token increases.

Patterns

Architectural Patterns

Choose based on coordination needs, not organisational metaphor.

Supervisor / Orchestrator — Use for centralized control when tasks have clear decomposition and human oversight matters. A single coordinator delegates to specialists and synthesises results. Trade-off: Supervisor context becomes a bottleneck; implement forward_message to prevent the telephone-game effect (~50% performance loss without it).
Isolation

Context Isolation Mechanisms

Select the right isolation mechanism for each subtask.

📋Instruction Passing

Create instructions via function call; the sub-agent receives only what it needs. Use for simple, well-defined subtasks. Maintains isolation but limits sub-agent flexibility.

Default choice

💾File System Memory

Agents read and write to persistent storage. The filesystem serves as the coordination mechanism, avoiding context bloat from shared state passing. Scales better than message-passing.

Use when shared state needed

🌐Full Context Delegation

Share the planner's entire context with the sub-agent. Use only for complex tasks where the sub-agent needs complete understanding. Partially defeats the purpose of context isolation.

Use sparingly
Failure Modes

Critical Failure Patterns

🔴
Supervisor Bottleneck: At 5+ workers, the supervisor spends more tokens processing summaries than workers spend on tasks. Cap workers per supervisor at 3-5 and add a second tier.
🔴
Telephone Game: Supervisors paraphrase sub-agent responses, losing fidelity. Implement forward_message to pass responses directly to users without synthesis.
🔴
Sycophantic Consensus: Agents in debate patterns converge on agreeable answers, not correct ones. Assign explicit adversarial roles and require agents to state disagreements first.
🔴
Error Propagation Cascades: One agent's hallucination becomes another agent's fact. Add validation checkpoints between agents — never trust upstream output without verification.
🔴
Over-decomposition: A 10-step pipeline with 10 agents spends more tokens on handoffs than on actual work. Decompose only when subtasks genuinely benefit from separate contexts.

Agent Memory Systems

Memory provides the persistence layer that allows agents to maintain continuity across sessions. The evolution from vector stores to temporal knowledge graphs represents increasing investment in structured memory.

Mem0 Zep / Graphiti Letta Cognee Temporal KG
Architecture

Memory Layers — Escalation Path

Start with the simplest layer. Add complexity only when retrieval quality degrades. Click each layer to expand.

⚡
Working Memory
Context window only · Scratchpad
Always
Place working memory content in attention-favored positions (beginning or end of context). Optimize the scratchpad with explicit structure. This layer is ephemeral — lost when the session ends.
📁
Short-term Memory
Session-scoped · File system / in-memory cache
Prototype
Store intermediate tool results and conversation state in structured JSON files with timestamps. Validates agent behavior before committing to infrastructure. Letta's filesystem agents scored 74% on LoCoMo — beating Mem0's 68.5% — confirming reliable retrieval beats tool sophistication.
🔍
Long-term Memory
Cross-session · Key-value store → Graph DB
Scale
Move to Mem0 or a vector store with metadata when the agent needs semantic search and multi-tenant isolation. Retrieve memories just-in-time — never preload everything, as large context payloads degrade attention quality. Place retrieved memories in attention-favored positions.
🕸️
Entity Memory
Cross-session · Entity registry + properties
Reasoning
Add Zep/Graphiti when the agent needs relationship traversal, temporal validity, or cross-session synthesis. Maintains identity ("John Doe" = same person across conversations). Graphiti uses generic relations keeping graphs simple; Cognee builds denser multi-layer semantic graphs with detailed relationship edges.
⏰
Temporal Knowledge Graph
Cross-session + history · Validity intervals
Complex
Use for facts that change over time, time-travel queries, and preventing context clash. Zep achieves 18.5% accuracy improvement on LongMemEval while reducing latency by 90%. Track both when events occurred and when they were ingested (bi-temporal model). Invalidate but never discard — history matters for temporal queries.

Watch Out

Memory System Gotchas

⚠️
Stuffing everything into context: Loading all available memories is expensive and degrades attention quality. Use just-in-time retrieval with relevance filtering.
⚠️
Ignoring temporal validity: Facts go stale. Without validity tracking, outdated information poisons the context and the agent acts on wrong assumptions.
⚠️
No consolidation strategy: Unbounded memory growth degrades retrieval quality over time. Set memory count thresholds or scheduled intervals to trigger consolidation.
⚠️
Embedding model mismatch: Writing memories with one embedding model and reading with another produces poor retrieval. Pin a single embedding model per memory store.
⚠️
Stale memory poisoning: Old memories that contradict current state corrupt agent behavior silently. Implement expiry policies or confidence decay, and surface contradictions explicitly.
